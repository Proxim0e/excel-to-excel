# Концепция: AI-ассистент оценки тендеров на мед. изделия

23 окт. 2026 г. · Ivan. Копия документа-концепта, чтобы он жил рядом с кодом. План работ — в [ROADMAP.md](ROADMAP.md), архитектурные решения — в [adr/](adr/).

## Цель и принципы

Цель — софт, который сам разбирает оферты участников тендеров на мед. изделия, заполняет Excel и предлагает решение по каждому участнику и лоту, опираясь на опыт прошлых лет. Человек вмешивается только там, где система не уверена.

- **Смысл, а не места.** Логика работает с полями (лот, модель, цена), а не с колонками и ячейками. Новый формат поставщика ломает только свой адаптер.
- **Спросить один раз.** Новый шаблон или несошедшиеся проверки — вопрос человеку. Ответ запоминается, и в следующий раз шаблон обрабатывается молча.
- **Лучше остановиться, чем записать мусор.** Каждая распознанная строка проходит проверки. Не прошла — в карантин с понятной причиной, а не в Excel.
- **Система советует, решает человек.** Особенно для альтернатив, образцов и вопросов рабочей группы.
- **База — главный актив.** Решения с причинами, проверки моделей, цены по годам ценнее любой модели ИИ.

## Что уже есть

Создание Excel по лотам и заполнение данными с сайта (участники, цены, документы) работает. Самое слабое место — распознавание технических и ценовых спецификаций из PDF участников.

| Источник | Что в нём | Состояние |
|---|---|---|
| achizitii.md | лоты, участники, цены, документы | скрапер работает, PDF скачиваются |
| PDF оферт (Anexa 22, 23) | модель, производитель, страна, спецификация, AMDM, цены | ~95% из Word/Excel, текст выделяется; сканов нет |
| Excel новой версии макета (CDM26, CDM26-2, CDM27_B, CPAS27) | решения по участникам и лотам, проверки, картинки | богатая разметка: текст + цвет + суффикс листа |
| Excel старой версии макета (2024, Consumabile tip deschis) | то же, другой макет | решение закодировано цветом, метки слабее |
| Нужды больниц до замены на номенклатуру | исходные формулировки | хранятся, ещё не смотрели |

Масштаб: до 300 лотов и до 50 компаний в тендере; около 8800 файлов, из них уникальных 700–900, остальное — повторы. Архив — 20+ Excel за 2–3 года. Железо: моноблок Lenovo 20 ГБ, ноутбук 16 ГБ, без видеокарты.

Процедуры: 880 — базовый список (номенклатурные лоты, ~75% спецификаций ясны), 214 — часть 1 из 3 дополнительного списка (~900 персональных лотов больниц за год).

## Модель данных

Центральное событие — **оферта**: участник предлагает модель на лот тендера, по ней принимается решение. Из истории оферт строятся паспорт модели, связь участник–продукт и вся аналитика.

Документы участника (Anexa 22, 23, даташиты, сертификаты) — источник доказательств для паспорта модели; копия реестра AMDM подтверждает регистрацию. Потребности бенефициаров привязаны к номенклатурному коду и сравниваются с их оборудованием: так ловятся аномалии вроде 50 годовых сервисных наборов на 1–2 аппарата.

## Рабочий процесс: Excel и база

Во время тендера рабочая поверхность — Excel; база получает финальный снимок после завершения процедуры и в Excel обратно не пишет. Так ручные правки никогда не перезаписываются.

| Когда | Где работаешь | Что делает система |
|---|---|---|
| Подготовка тендера | Excel | создаёт листы лотов, заполняет данные с сайта (уже работает) |
| Оценка | Excel | пишет подсказки только в отведённые ячейки и на лист «Проверить», твои ячейки не трогает |
| Вопросы к тебе | лист «Проверить» | новый шаблон PDF, карантин распознавания, жёлтые проверки AMDM — одна строка на вопрос, ответ в соседней колонке |
| После завершения | — | импорт итогового Excel в базу как снимок: решения, причины, события, доказательства |

Лист «Проверить» — первый интерфейс «спросить один раз»; локальная веб-страница — позже, когда вопросов станет больше, чем удобно держать в Excel.

## Распознавание PDF оферт

Схема у всех одна (типовые Anexa 22 и 23), различается только макет. Поэтому задача — сопоставить чужой макет с известными полями, а не распознать любую таблицу.

**Сначала — сортировка документов.** Из ~8800 файлов тендера уникальных 700–900, а нужные лежат где угодно, поэтому до распознавания идут два шага:

1. Дедупликация по содержимому (хеш файла), а не по имени или ссылке: один файл обрабатывается один раз, остальные — ссылки на него.
2. Классификация каждого уникального файла по тексту первых страниц — сначала правила по ключевым словам, LLM только для неопознанных:

| Тип | Куда идёт |
|---|---|
| Anexa 22 (техническая спецификация) | распознавание → позиции оферты |
| Anexa 23 (ценовая спецификация) | распознавание → цены |
| Даташит, брошюра, каталог | доказательства для параметров, паспорт модели |
| ISO 13485, ISO 9001, DoC, CE | проверка качества |
| Регистрация AMDM, авторизация производителя | доказательства в паспорте модели и связи участник–продукт |
| Прочее (договоры, выписки, гарантии) | архив, не обрабатывается |

По даташитам система ищет подтверждение конкретных значений: заявлено «18 G» в Anexa 22 → найдено ли «18 G» в даташите той же модели и на какой странице.

**Распознавание:**

1. **Геометрия.** PDF → слова с координатами из текстового слоя, без OCR. Колонки — по x-границам строки заголовков, а не по линиям таблицы. Новая строка — там, где появилось значение в колонке «Nr. Lot» или «CPV».
2. **Смысл.** Ячейки → поля по профилю шаблона: «заголовок → поле» + границы колонок.
3. **Профиль шаблона.** Ключ — отпечаток заголовков и тип документа, а не имя компании. Знакомый — молча; новый — черновик маппинга + превью трёх строк человеку → подтвердил → сохранено. Ожидается 20–30 профилей.
4. **Сверка с тендером** — главный контроль качества: требование совпадает с требованием лота; количество = количеству лота; цена × количество = сумма (цены без TVA).
5. **Карантин.** Строка не прошла сверку → «сломалось распознавание», вопрос человеку, а не вердикт участнику.
6. **Запасной путь.** Не сошлось после профиля → LLM читает страницу в заданную схему; результат проходит те же сверки.

Качество меряется на архиве: строки 3 и 11 Excel — эталон того, что должно было извлечься из PDF.

## Оценка и процесс решения

Оценка — процесс с этапами (уточнения → образцы → бенефициар / рабочая группа → решение), поэтому система подсказывает следующий шаг, а не только «да/нет».

**Кодбук** — одна страница с правилами разметки, на которую опираются импортёр, база и интерфейс:

| Метка | Где | Значение |
|---|---|---|
| Зелёный | ячейки / вкладка | соответствует |
| Светло-зелёный | ячейки / вкладка | соответствует декларативно или под копирку (УЗИ, КТ) — низкая уверенность |
| Красный | ячейки / вкладка | не соответствует |
| Голубой | ячейки / вкладка | обсуждение на рабочей группе (с 2027); в старых файлах также альтернативы, «Nu a fost evaluat» и шаблонные «Tehnic corespunde» |
| Синий | ячейки / вкладка | альтернатива (с 2027) |
| Жёлтый | ячейки / вкладка | нужны уточнения |
| Тёмно-синий | вкладка | закупка не состоялась |
| Ad | имя листа | альтернатива по умолчанию, решение офиса |
| A или без пометки | имя листа | альтернатива с уточнением у бенефициара |
| M | имя листа | запрошены образцы |

Вердикт — три уровня: **лот** (цвет вкладки + суффикс), **участник** (текст и цвет строки 1: текст — техническое мнение, цвет — итог; могут расходиться), **события** (уточнения, образцы, бенефициар, рабочая группа).

Уточнения в Excel: цвет решения дублируется в ячейке с предложенной спецификацией; при жёлтом справа от колонки участника вставляется колонка «clarificări» с ответом; ячейка ответа красится по результату. Колонки «clarificări» относятся к участнику слева, а не к новому участнику.

Нормализованная причина решения сводится к трём осям: **решение** (corespunde / nu corespunde / alternativa A, Ad / în discuție / ne evaluat), **основание** (документы, образцы, бенефициар, рабочая группа, уточнения), **причина** (AMDM, параметр, нет в Anexa 22, образец не подошёл, нет ответа, copy-paste, нестабильная оферта). «Nu a fost evaluat» — не отказ и не идёт в обучение.

Правила (на любом CPU): обязательные поля, номер AMDM, копия требования, числовые параметры, количество, бюджет, цена против истории. Расхождение параметра — всегда «проверить», не «отклонить».

Альтернативы: история принятых A/Ad показывает реальные допуски — система предлагает «вероятная альтернатива, такие принимались в 2025».

Риск и образцы: выше — новый производитель, критичная совместимость, проблемы в прошлом, декларативное «compatibil»; ниже — малое количество, хорошая история модели, фото разъёма.

## База знаний

Проверки привязываются к **модели**, а не к лоту. Паспорт модели: проверенные параметры с доказательствами, совместимость, результаты образцов по годам, регистрация AMDM, проблемы. Формат ячейки «копия из Anexa 22 // что нашёл» разделяется импортёром по `//`. Доказательства хранятся отдельными файлами и привязаны к записи «модель → параметр».

Реестр оборудования бенефициаров: больница → аппарат → вариант. Связь участник–продукт выводится из истории оферт (участник × модель × лот × тендер × год × цена × итог), эксклюзивность не задаётся вручную.

## Проверка регистрации и качества

Номер DM000… проверяется в реестре AMDM (registru.dispozitive.amdm.gov.md): найти номер в оферте → запросить запись (вежливо, с кешем) → сравнить производителя, модель/каталожный номер, название с нечётким совпадением → зелёный / красный «nu este înregistrat» / жёлтый на проверку.

Реестр открытый, без капчи, ~627 тыс. записей, Export CSV ограничен 5000 записями. Стратегия: поиск по требованию с кешем; полное зеркало — позже, частями по датам приказа. Копия отстаёт до недели: не найденный номер перепроверяется на сайте. Наличие записи не гарантирует действующую регистрацию — это фиксируется в отчёте.

Немедицинские изделия: ISO 13485 → ISO 9001 → DoC; проверяются производитель и срок. Дата валидности — переход тендера в статус «evaluare» на achizitii.md.

## Управление номенклатурой

Доп. списки (~900 лотов в год) анализируются, чтобы пополнить базовый список: перенести в базовый, привязать к существующему коду, объединить лоты, улучшить спецификацию, удалить неиспользуемые. Главный датасет — прошлые замены «исходная формулировка → код».

Две таблицы фактов: оферты (участник × модель × лот × тендер × год × цена × итог) и потребности (бенефициар × код × год × количество). ## ИИ: локально и через API

| Слой | Что делает | Где работает |
|---|---|---|
| Правила и сверки | поля, параметры, AMDM, арифметика, история цен | любой CPU, секунды |
| Точный поиск | похожие лоты по коду, паспорт модели | SQLite |
| Поиск по смыслу | похожие лоты без кода, дубликаты | маленькая embedding-модель на CPU |
| Локальная LLM 7–8B | советник по спорным позициям | Ollama, пачкой на ночь |
| Платный API | тонкие случаи, маппинг нового шаблона | по запросу |

Выход любой модели структурированный и проходит те же сверки; «не соответствует» от модели — «проверить». Своя дообученная модель — не раньше тысяч размеченных решений. Ядро — библиотека, отдельная от интерфейса; SQLite со схемой, готовой к переезду на Postgres; никаких жёстких путей.

## Как мерить успех

Часы на оценку тендера; доля позиций, решённых без человека; доля изменённых решений (главная метрика качества); точность распознавания по полям против эталона из архива; число вопросов «спросить один раз» на тендер. Целевые значения — после первого пилота.
